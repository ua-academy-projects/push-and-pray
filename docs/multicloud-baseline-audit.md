# OilScope multi-cloud baseline audit

Audit date: 2026-09-17

This document records the repository and read-only cloud baseline before the
configuration contract is migrated to the versioned AWS/GCP model described in
`TZ-oilscope-multicloud.md`. It is evidence, not a statement that the current
deployment is healthy.

## Audit boundaries

- No `terraform apply`, state import, resource deletion, DNS mutation, image
  publication, or secret read was performed.
- Secret containers were listed by name only. Secret values and Terraform state
  attributes were not printed.
- Local state was inspected by address and resource type only.
- The active cloud targets were checked before querying live resources.

## Entry points and state

| Concern | Current implementation | Assessment |
| --- | --- | --- |
| AWS root | `infrastructure/terraform/stacks/aws` | Keep. It avoids initialising the GCP provider for an AWS-only deployment. |
| GCP root | `infrastructure/terraform/stacks/gcp` | Keep. It avoids initialising the AWS provider for a GCP-only deployment. |
| Mixed root | `infrastructure/terraform` | Preserve for state compatibility, but do not expose it as a supported deployment mode in the new contract. |
| Deployment wrapper | `scripts/deploy-cloud.sh` | Refactor into explicit validate/plan/apply phases. It currently performs too many state-changing operations in one command. |
| Backend | Local backend with `.state/<profile>.tfstate` | Does not meet the remote encrypted/locked state requirement. Provider/environment/deployment-specific backend config must be generated by foundation bootstrap. |
| Foundation bootstrap | Not present | Required. Add a separate idempotent `scripts/bootstrap-cloud.sh`; it must never launch the workload deployment. |

The ignored local state directory exists and contains `gcp.tfstate`,
`mixed.tfstate`, historical plans, and backups. The current state files are not
an authoritative inventory:

- `gcp.tfstate` still records APIs, secret containers, network-related
  resources, identities, reserved addresses, registry, and monitoring objects;
- the live GCP inventory no longer contains the recorded VPC, VM, Cloud SQL,
  Artifact Registry, or Secret Manager objects;
- `mixed.tfstate` records a partial GCP network/private-service baseline even
  though the corresponding live network is absent;
- `custom.tfstate` currently has no resources.

Therefore any future plan must first use a dedicated state/live reconciliation
procedure. It is unsafe to import, forget, recreate, or destroy these addresses
as part of an unrelated refactor.

## Terraform implementation

### Already useful

- AWS and GCP have separate provider modules and isolated root stacks.
- Logical machine, image, and disk profiles are resolved by
  `modules/config`.
- RDS and Cloud SQL are private and export password-free connection metadata.
- AWS uses private DB subnets; Cloud SQL uses Private Service Access.
- Bastion and workload SSH paths are separated.
- VM, secret-access, database, registry, and monitoring resources are already
  decomposed enough to refactor incrementally.
- AWS/GCP module tests use mocked providers and currently pass.

### Must be changed

- The schema has no `schema_version`, `cloud_provider`, `data_profile`, or
  `deployment_runtime`. It still uses `default_cloud` and `manage_db`.
- Per-VM `cloud` overrides and a supported `mixed` profile conflict with the
  current task scope. Overrides must be accepted only when equal to the global
  provider; cross-cloud values must fail early.
- AWS AMIs are hard-coded in JSON. A region/architecture-aware lookup with
  deterministic owner and name filters is required.
- Common configuration exposes provider terminology through `network_tags`.
  The public contract should use logical access profiles.
- Outputs are incomplete and differ between the isolated stacks and mixed root.
  They lack one complete, versioned deployment/node/database/registry/ingress/
  monitoring contract.
- DNS is changed by direct Cloudflare API calls in `deploy-cloud.sh`, not owned
  by Terraform.
- Application images remain sourced from GHCR at runtime. Only Redis and
  RabbitMQ are mirrored to ECR/Artifact Registry.
- Upstream Redis/RabbitMQ references use moving tags without pinned digests.
- The GCP 5xx metric parses text with a regular expression instead of a stable
  structured status field.
- Backend selection is local and profile-based rather than environment/provider/
  deployment-based remote state.

## Runtime and application contracts

### Portable data profile

The code already implements the intended portable behavior:

- PostgreSQL runs on a private VM from the custom database image;
- `observation_queue` uses SQL with visibility timestamps and
  `FOR UPDATE SKIP LOCKED`, not a managed-only PostgreSQL extension;
- UI sessions are stored in PostgreSQL as hashed identifiers and JSONB;
- persistent Compose volumes are used.

The legacy CI job name and comments still refer to PGMQ, and the development
database image contains PGMQ, but the current application queue implementation
uses the portable SQL tables in migration `004_create_observation_queue.sql`.
Documentation and test names should be corrected without removing the extension
until image compatibility is deliberately changed.

### Managed data profile

The code already supports:

- RDS PostgreSQL or private-IP Cloud SQL;
- RabbitMQ queue backend;
- Redis session backend;
- RabbitMQ and Redis containers on the private History VM;
- provider secret stores and password-free Terraform outputs.

Keeping the managed services on History is the least disruptive current
topology. Moving them to a new infra VM would add cost and migration risk, so it
is deferred until availability or isolation requirements justify it.

### Environment interface

The services already consume provider-neutral settings:

- `DATABASE_URL`;
- `QUEUE_BACKEND` and RabbitMQ settings;
- `SESSION_BACKEND` and `REDIS_URL`;
- History service endpoint;
- `SESSION_COOKIE_SECURE`.

No application service needs to branch on AWS versus GCP. This contract should
be retained.

## Ansible

### Already useful

- Inventory is generated dynamically from Terraform outputs.
- Hosts are grouped by logical role.
- Workloads connect through a bastion/ProxyJump path.
- Roles are capability-oriented: baseline, Docker, Compose, registry auth,
  secrets, database connection/migrations, application roles, edge proxy, and
  cloud monitoring agents.
- Secrets are resolved at deployment time rather than stored in inventory.

### Must be changed

- Inventory must consume the new versioned normalized output instead of several
  legacy output shapes.
- Cloud-specific monitoring/auth tasks should remain small adapters behind
  common roles.
- Idempotency needs an automated second-run test; syntax checks alone do not
  prove idempotency.
- The current edge proxy is Traefik. It can be retained because the task permits
  a working existing reverse proxy, but external DNS/TLS/port acceptance still
  needs explicit verification after an authorised live deployment.

## CI and image delivery

- Fetcher, History, UI, and database images are built by GitHub Actions.
- The reusable workflow publishes an immutable full commit-SHA tag and OCI
  source/revision/description labels.
- README claims additional moving tags, but the current workflow publishes only
  the full SHA tag. Code is the current truth.
- No workflow currently promotes the same application digest from GHCR to ECR
  or Artifact Registry.
- OCI version/build-time labels and digest-equality verification are missing.
- Security, language, integration, frontend, Terraform, and Ansible checks are
  present in varying scopes; bootstrap tests do not exist because bootstrap is
  not implemented.

## Monitoring and logging

- AWS and GCP modules contain dashboards/alerts and external HTTPS checks.
- CloudWatch/Ops agents are represented as Ansible roles.
- The application currently emits conventional text logs, not the required
  structured request log with `status`, duration, route, and correlation ID.
- Existing 5xx extraction is consequently regex-based and can produce false
  positives/negatives.

Structured access logging must be introduced before treating the HTTP 5xx
metric as an application acceptance signal.

## Documentation drift

- `docs/multi-cloud-deployment-uk.md` advertises `mixed` as supported, while the
  new task explicitly excludes it.
- README moving-tag claims do not match the image workflow.
- Documentation describes local state as the current mechanism but does not
  provide the required foundation bootstrap and remote-state workflow.
- Terraform success and historical live experiments are documented more fully
  than present application acceptance. No current end-to-end deployment is
  proven healthy.

## Refactor order

1. Freeze the normalized contracts and introduce a backward-compatible schema
   migration.
2. Add tested foundation bootstrap and generated backend manifests.
3. Make the AWS/GCP isolated stacks the only supported roots for the current
   schema; retain mixed code only for state/history compatibility.
4. Complete normalized outputs and adapt inventory.
5. Replace provider-native public configuration fields with logical mappings,
   including deterministic AMI lookup.
6. Complete portable/managed validation and private access policies.
7. Promote all application and third-party image digests to the selected cloud
   registry.
8. Move Cloudflare DNS under Terraform and retain the existing proxy behind the
   provider-neutral ingress contract.
9. Add structured request logging and provider monitoring adapters.
10. Run the four static plan profiles. Run live acceptance only after separate
    authorisation and state reconciliation.
