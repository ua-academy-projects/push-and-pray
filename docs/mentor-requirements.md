# OilScope mentor requirements

This records architectural and review constraints supplied with project history, not a substitute for current code. For current behavior, inspect the [architecture map](architecture-current.md), [project-config schema](../infrastructure/terraform/project-config.schema.json), and affected source. If a requirement and implementation disagree, report both with evidence before changing the design. [Architecture decisions](architecture-decisions.md) records selected superseded and mode-dependent choices.

| Requirement | Decision boundary and current evidence |
| --- | --- |
| Keep Terraform root cloud-agnostic. | Root [main.tf](../infrastructure/terraform/main.tf) should orchestrate shared config into provider modules. Resolve provider instance types, images, disks, and location selection in the AWS/GCP/Azure modules, not by growing root [locals.tf](../infrastructure/terraform/locals.tf) into a provider-specific mapping layer. Check relevant cloud parity without forcing unrelated providers to change. |
| Preserve one project-config contract. | The [schema](../infrastructure/terraform/project-config.schema.json) defines shared logical fields and provider mappings. Avoid adding a parallel provider selector or duplicating mapping logic. Optional VM bootstrap commands and additional disks already exist in the inspected schema/modules; historical simplification notes do not erase current support. |
| Keep logical VM roles stable. | Bastion, database, history, fetcher, and ui are deployment contracts, not disposable names. The database VM remains in managed mode for migrations/provisioning. Root Terraform and [inventory](../infrastructure/ansible/oilscope/platform/plugins/inventory/oilscope.py) both normalize bastion context today. Preserve parity; do not add a third independent set of defaults. A deduplication refactor would need separate scope and verification. |
| Keep SSH topology in inventory. | The custom inventory owns cloud discovery, role groups, private host addresses, bastion selection, and SSH proxy arguments. Do not restore removed group_vars SSH/ProxyCommand duplication. See [inventory documentation](../infrastructure/ansible/inventory/README.md). |
| Keep managed PostgreSQL private. | RDS, Cloud SQL, and Azure Flexible Server use provider-specific private networking. Do not expose a database publicly to fix connectivity. Trace subnet/VPC or VNet, firewall/security group, private DNS, Terraform metadata, and application connection settings. See [database modes](database-modes.md) and [Azure](azure.md#managed-postgresql-and-secrets). |
| Preserve both database architectures. | postgres_extensions uses self-managed PostgreSQL, PGMQ, and PostgreSQL sessions; managed uses cloud PostgreSQL, RabbitMQ, and Redis. The [schema](../infrastructure/terraform/project-config.schema.json) has one project-wide database_mode, and default_cloud selects the managed provider. Do not collapse modes or invent an additional selector. |
| Prove scenarios end to end. | A successful Terraform plan proves neither workload health nor cross-cloud application connectivity. When requested to claim a supported cloud scenario, verify infrastructure, inventory/SSH, image access, runtime, service dependencies, and user-facing endpoint. Do not claim one cross-cloud K3s cluster without implemented reachability and actual tests. |

## Working agreements

For requested fixes, inspect the affected contract and callers, make the smallest viable diff, and avoid unrelated resource renames, module moves, formatting, or public config changes. Verify locally with checks appropriate to the touched layer. Terraform formatting/validation and Ansible syntax/lint are useful; Terraform plan needs the appropriate environment and is not deployment proof. Kubernetes manifest checks do not prove application health. Do not run infrastructure mutations or discard Git work without an explicit user request.

Cloudflare defaults and UI public-IP derivation were deliberately placed in [cloudflare.tf](../infrastructure/terraform/cloudflare.tf), not root locals. Native monitoring is already implemented across the three providers; historical Prometheus/Blackbox work is not a reason to add another monitoring stack. See [architecture decisions](architecture-decisions.md).
