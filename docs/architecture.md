# Архітектура

## Компоненти

| Сервіс | Порт (за замовч.) | Відповідальність |
|---|---|---|
| **UI Service** | 5000 | Показує сторінку, приймає дії користувача, звертається ЛИШЕ до Proxy |
| **Proxy Service** | 5001 | Викликає публічне API (Open-Meteo), пересилає дані в Backend, віддає результат у UI |
| **Backend Service** | 5002 | Єдиний сервіс з доступом до БД. Зберігає та повертає історію запитів |
| **PostgreSQL** | 5432 | Реляційне сховище історії запитів |

## Потік "Отримати поточну погоду" (тільки Poller)

Користувач через UI **більше не може** ініціювати виклик публічного API.
Єдине джерело нових даних - `poller-service`, який з заданим інтервалом
сам звертається до Proxy:

1. Poller викликає `GET /api/current?city=...` на Proxy (за таймером,
   без участі користувача).
2. Proxy:
   - геокодує назву міста через Open-Meteo Geocoding API;
   - отримує поточну погоду через Open-Meteo Forecast API;
   - надсилає `POST /history` у Backend Service для збереження.

Ендпоінт `/current` у UI-сервісі навмисно **видалений** - у коді немає
жодного шляху, яким користувач міг би ініціювати цей виклик. У
`docker-compose.yml` порт Proxy (`5001`) також не проброшений назовні
(немає `ports:`), тож викликати `/api/current` напряму, в обхід Poller,
неможливо навіть через `curl` з хост-машини - лише зсередини Docker-мережі.

## Потік запиту "Переглянути історію" (єдина дія, доступна користувачу)

1. UI Service отримує `GET /history` від браузера.
2. UI Service звертається до Proxy: `GET /api/history`.
3. Proxy звертається до Backend Service: `GET /history`.
4. Backend Service читає останні записи з PostgreSQL і повертає їх по ланцюжку назад.

## Автономне оновлення даних (Poller)

Окрім оновлення "по кліку" (описано вище), `poller-service/poller.py` -
окремий процес (окрема папка, окремий `Dockerfile`, свій мінімальний набір
залежностей - лише `requests`, без Flask), що з заданим інтервалом
(`POLL_INTERVAL_SECONDS`, за замовчуванням 15 хв) автоматично звертається
до `GET /api/current` для кожного міста зі списку `WATCHED_CITIES` - так
само, як це робив би UI.

Це навмисно **не новий "четвертий сервіс"** з окремими межами відповідальності,
а просто ще один клієнт Proxy - Poller не знає про публічне API чи БД
безпосередньо, він лише повторно використовує вже існуючий ендпоінт.
Завдяки цьому:

- Backend service накопичує реальну динаміку даних у часі, навіть якщо
  ніхто не відкриває UI;
- логіка геокодування/збереження не дублюється - вона лишається лише в
  Proxy;
- Poller легко стає окремим контейнером / Kubernetes CronJob у майбутніх
  заняттях, без переписування коду - це вже готовий, ізольований процес.

## Чому саме так

- **UI ніколи не знає** про публічне API чи базу даних — його можна повністю переписати
  (наприклад, на React) без змін у Proxy чи Backend.
- **Proxy — єдина точка оркестрації**: якщо публічне API зміниться (наприклад, на інший
  постачальник погоди), міняється лише proxy-service.
- **Backend — єдиний власник persistence-логіки**: схему бази даних, тип БД чи навіть
  СУБД (PostgreSQL → MariaDB) можна змінити, не чіпаючи інші сервіси, оскільки вони
  спілкуються з Backend лише через HTTP API.
- Такий поділ спеціально готує проєкт до майбутніх завдань: контейнеризації (кожен сервіс
  — окремий образ), оркестрації (кожен сервіс — окремий under Kubernetes deployment),
  CI/CD (окремі пайплайни на сервіс) та хмарного деплою.
