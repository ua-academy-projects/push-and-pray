# Azure secrets module

One Key Vault, RBAC-authorized, plus one role assignment per (VM identity,
secret) pair the project configuration maps.

## Terraform owns the grant, not the value

Secrets Manager and Secret Manager both let Terraform create an empty secret
*container* and leave the value to the deployment controller. A read before the
first version fails, which is what you want.

Key Vault has no container: `azurerm_key_vault_secret` requires `value` or
`value_wo`. Writing a placeholder would not be the safe equivalent — a workload
reading too early would get a successful read of the **wrong credential**
instead of a failure. So this module creates no workload secret at all. It
creates the grants; `secret_versions` (Phase 2) writes the first version.

The one exception is the managed database administrator credential, which the
database module writes here. That mirrors the Cloud SQL exception: the password
is generated by Terraform and therefore lives in state. No workload identity is
granted access to it.

## Grant scopes

A grant is written against the ARM scope

```text
<vault ARM ID>/secrets/<secret name>
```

while the workload reads the data-plane URI

```text
https://<vault>.vault.azure.net/secrets/<secret name>
```

These are different strings for the same secret. `secret_resource_names`
exports the URI, so the resolver never has to rebuild a name or mistake one for
the other.

Because the grants are written before any version exists, an apply that runs
into an ARM scope error here means the order has to be inverted for that
subscription: upload the first versions, then apply. Nothing in this module
falls back to a vault-wide `Key Vault Secrets User`, which would hand every VM
every secret including the database administrator's.

## Naming

Vault names are globally unique, 3–24 characters, letters, digits and hyphens.
Set `clouds.azure.key_vault.name` to choose one; otherwise the module derives
`<prefix truncated to 17>-<6 hex of subscription/resource-group>`, which is
stable across applies rather than random.

Secret IDs come straight from `secret_mappings`. Key Vault accepts
`[A-Za-z0-9-]{1,127}` and treats names case-insensitively, so an ID containing
`_` — which the shared schema allows for AWS and GCP — is not usable here.

## Deletion

`soft_delete_retention_days` and `purge_protection_enabled` are both explicit in
`clouds.azure.key_vault`. A deleted vault keeps its *name* reserved for the
retention period; with purge protection on it cannot be released early. The
provider is configured to recover a soft-deleted vault rather than purge one, so
a redeploy under the same name reattaches instead of failing.

## Writer access

`azure_secret_version_managers` (root variable) grants `Key Vault Secrets
Officer` on the vault. Key Vault has no add-a-version-only role, so this is
genuinely privileged: name the deployment controller, never a workload identity.
